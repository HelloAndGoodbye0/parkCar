## 1. 二期愿景与目标

一期已建成「人工 + 半自动」的停车场管理系统（出入场登记、计费、月卡、报表），核心痛点在于：

- 出入场仍需收费员**手工录入**车牌，高峰期排队；
- 道闸无法自动开合，车辆通行效率低；
- 车主无法自助缴费/续费，依赖窗口；
- 单场独立部署，无法支撑连锁停车场集团化运营；
- 营收、财务数据停留在报表展示，缺少对账与自动化。

二期目标（按业务价值排序）：

| 目标 | 说明 | 业务价值 |
| ---- | ---- | ---- |
| G1 无人化出入场 | 车牌识别 + 道闸联动，实现入场自动抬杆、出场识别计费 | 降人力、提效率 |
| G2 车主自助服务 | 小程序查费/缴费/月卡续费/车位预订 | 增收、降窗口压力 |
| G3 连锁化运营 | 多停车场统一管理、集团级报表 | 规模化扩张 |
| G4 财务数字化 | 对账、发票、日结自动化 | 账务合规、降差错 |

> 二期不做：无人值守全托管的 AI 代泊、会员储值卡余额生息、停车保险等衍生金融业务。

## 2. 二期范围（In Scope / Out of Scope）

### 2.1 包含范围

| 板块 | 包含功能 |
| ---- | ---- |
| A 智能设备接入 | 车牌识别相机对接、道闸控制对接、设备在线监控、异常补录 |
| B 车主小程序 | 注册登录（手机号+车牌）、查费、微信支付、月卡自助办理/续费、车位预订、发票申请 |
| C 多场连锁 | 停车场/门店管理、跨场数据权限、集团报表、统一收费策略模板 |
| D 财务数字化 | 支付对账、日结单、发票管理、营收分账 |
| E 技术底座升级 | Redis 缓存/分布式锁、消息队列、对象存储、WebSocket 实时推送、定时任务中心 |

### 2.2 不包含范围（三期候选）

- 车位引导屏/地锁联动、反向寻车；
- 会员储值钱包（预付卡）与跨场通用会员体系；
- 与第三方 ERP / 财务系统深度集成；
- 夜间无人值守自动收费机器人。

## 3. 用户角色（二期扩展）

| 角色 | 端 | 说明 | 主要权限 |
| ---- | ---- | ---- | ---- |
| 系统管理员 | 管理端 | 停车场运营方总部 | 全部功能，含连锁配置、财务对账 |
| 场长/值班员 | 管理端 | 单场运营者 | 本场出入场、设备、异常处理、日结 |
| 收费员 | 管理端 | 现场操作人员 | 出入场登记、收费、异常补录 |
| 车主 | 小程序 | 停车消费者 | 查费、缴费、月卡、预订、发票 |
| 设备终端 | HTTP 对接 | 相机/道闸 | 上报识别结果、接收开闸指令 |

> 连锁模式下引入「场长」角色，数据权限收敛到单场（通过 `lot_id` 隔离）。

## 5. 非功能需求（二期强化）

| 类别 | 要求 |
| ---- | ---- |
| 性能 | 设备识别到开闸 ≤ 2s；小程序缴费支付回调处理 ≤ 1s；单场日流量支撑 5000+ 车次 |
| 可用性 | 道闸联动场景核心链路 99.95%；设备断网时可本地缓存入场记录（离线模式） |
| 安全 | 设备接口使用独立 API Key + 签名；支付回调验签；敏感信息（手机号）脱敏；HTTPS 全链路 |
| 一致性 | 开闸与停车记录强一致（失败补偿）；支付回调幂等；对账差异可追溯 |
| 可扩展性 | 设备协议层抽象（可适配多家相机品牌）；连锁扩展仅需加 `lot_id` |

## 6. 关键业务规则

1. **自动入场**：识别车牌 → 命中黑名单（全集团或本场）→ 不抬杆 + 抓拍留存；月卡有效 → 直接抬杆入场；临时车 → 抬杆入场并分配车位。
2. **自动出场**：识别车牌 → 已缴清 → 抬杆放行；未缴费 → 不抬杆，推送缴费提醒；月卡有效 → 直接抬杆。
3. **人工兜底**：识别失败/无牌车/黑名单，收费员在管理端补录车牌、核对后手动抬杆，全程留痕。
4. **缴费幂等**：同一订单支付回调只生效一次；重复缴费自动退款（或提示已支付）。
5. **月卡有效期**：跨场白名单模式下，月卡在集团所有场生效，优先按本场规则校验。
6. **对账口径**：以微信/支付宝官方账单为准，本地订单为辅助，差异单进入人工复核。

## 7. 里程碑与迭代计划

| 阶段 | 周期 | 交付物 | 说明 |
| ---- | ---- | ---- | ---- |
| M1 技术底座 | 第 1-2 周 | Redis 接入、定时任务、文件存储、WebSocket | 基础设施就绪 |
| M2 设备接入 | 第 3-6 周 | 相机识别对接、道闸控制、设备管理、自动出入场 | 核心闭环（联调真机） |
| M3 车主小程序 | 第 6-10 周 | 小程序注册登录、查费缴费、月卡办理续费 | 车主自助（含微信支付） |
| M4 连锁化 | 第 11-13 周 | 停车场管理、lot_id 改造、数据权限、集团报表 | 可扩展部署第二场 |
| M5 财务数字化 | 第 13-15 周 | 对账、日结、发票 | 财务闭环 |
| M6 联调验收上线 | 第 15-18 周 | 全量回归、真机压测、灰度上线 | 稳定发布 |

> 若单人或 2 人团队，建议砍掉 P2（预订、发票、模板下发）后压缩至 12~14 周。

## 8. 风险与依赖

| 风险 | 影响 | 应对 |
| ---- | ---- | ---- |
| 相机品牌协议不统一 | 设备接入返工 | 采购前确认支持 HTTP API / SDK；协议层做适配器 |
| 微信支付商户号申请周期 | 小程序上线延迟 | 提前 2 周申请，准备营业执照等资质 |
| 真机联调场地受限 | 自动出入场验证不足 | 用模拟相机（录制视频流）先联调，再到场实测 |
| 现有单场数据迁移 | 连锁改造破坏存量 | `lot_id` 默认值=原场 ID，SQL 迁移脚本先行 |
| 设备断网 | 入场记录丢失 | 相机端本地缓存 + 补传；后端兜底手工补录 |

## 9. 验收标准（样例）

- **A01**：模拟车牌「京A12345」入场，识别 → 自动分配车位 → 记录到场内列表，全流程 ≤ 2s；
- **A04**：后端下发开闸指令，道闸日志记录指令时间、结果，失败可重试；
- **B03**：小程序生成订单 → 微信支付 → 回调 → 订单状态「已支付」→ 道闸抬杆，重复回调不重复扣款；
- **B04**：小程序自助续费后月卡有效期正确顺延，管理端与小程序数据一致；
- **C02**：收费员 A（场1）只能查到场1数据，管理员可查全集团；
- **D01**：下载微信对账单后，本地订单与对账单金额一致率 100%，差异单可人工复核。

## 10. 需求确认清单（开发前需业务方答复）

1. 采购的相机型号与协议（HTTP API / SDK / 其他）？是否支持二次开发？
2. 微信支付商户号主体与小程序主体是否一致？是否已有？
3. 连锁首期计划部署几个场？是否需要跨场月卡互通？
4. 发票：首期是否需要？开票主体与税率？
5. 道闸品牌是否支持远程 HTTP 控制？有无安全互锁要求？
6. 无牌车/识别失败场景的现场 SOP（是否允许无牌车入场）？
7. 日结按「日」还是「班次」？现金收款是否需要上传支付凭证？
8. 是否已有云服务器/对象存储/备案域名？HTTPS 证书谁提供？
